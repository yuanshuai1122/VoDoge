## 1. 为什么重构

现在这套 VoDoge 是**单机自用**形态：一个 Go 二进制，管本机插着的几根 USB 模组，
一套网页给一个人用。它已经能跑，而且今天刚修完四个真 bug（见 §4）。

但它有三个结构性问题，决定了不能靠打补丁演进成 SaaS：

| 问题 | 现状 | SaaS 要求 |
|---|---|---|
| **单租户** | 全局配置、全局设备池、一套账号 | 每个企业客户看到且只能看到自己的设备与短信 |
| **必须公网可达** | 靠 WireGuard + 反向 SSH 隧道 + Caddy 拼出入口 | 客户机房在 NAT 后，设备必须**主动外拨**，云端零配置 |
| **断网即失能** | 数据库在云上，连不上就退出进程 | 断网时本地照常收短信、缓存；网一好自动补传 |

还有一个非结构性但同样重要的动机：**硬件差异现在是散在代码里的 if-else**。
今天为了定位「EC20 配电信卡收不到短信」花了一整天，最后发现是
「模组 × 运营商」的能力组合问题——这类知识必须变成**可声明的数据**，
而不是埋在分支里等人踩。这就是 §5 垂直工厂要解决的事。

### 明确不做的事

- **不迁移现有部署**。新架构是 greenfield，老的单机版继续作为参考与备用。
- **不追求代码复用**。业务语义一致，实现重新设计；照抄旧代码是被禁止的。
- **不做设备固件分发/OTA 刷机**。边缘端自更新在 §7.8，刷模组固件不在范围内。

### 连接方向（不可协商的约束）

**所有连接都是边缘端主动发起。** 云端**永远不会**、也**不可能**主动连边缘端。

原因：客户机房在 NAT/防火墙后，要求客户开端口映射会直接劝退销售。
这条约束决定了：

- 指令下发必须走**已建立的反向长连接**，不是 HTTP 回调
- 边缘端离线时，指令要在云端**排队**，不是失败
- 边缘端的身份认证在**连接建立时**完成一次，不是每条消息

### 两个仓库

| 仓库 | 内容 | 语言 |
|---|---|---|
| **`vodoge-edge`** | 边缘端全部 | Rust |
| **`vodoge-cloud`** | 控制台 + 网关 + 数据库迁移 + 共享协议定义 | TypeScript / Go / SQL |

`vodoge-cloud` 内部用 monorepo 分包（§6.2）。网关虽是 Go、控制台是 TS，
但它们**同生共死**（一次发版要同时上线，共享数据库 schema 与 Redis 频道约定），
放同一个仓库比跨仓库对版本更省事。

> 若未来网关需要独立扩容节奏，再拆第三个仓库。届时先把 §9 协议规格
> 与 §10 数据模型抽成独立的 `vodoge-contract` 包，两边都依赖它。

## 3. 分层职责：什么在云端，什么在客户端

这是本次重构最容易出错的地方，先用一张表钉死。

| 能力 | 边缘端 | 云端 | 判据 |
|---|---|---|---|
| 模组发现、驱动绑定 | ✅ 独占 | ✗ | 需要访问 `/dev`，物理绑定 |
| AT/QMI 指令执行 | ✅ 独占 | ✗ | 同上 |
| 短信**收取**与解码 | ✅ 独占 | ✗ | 必须贴着硬件，且断网要能继续 |
| 短信**存储** | 缓存（滚动保留） | ✅ 权威 | 云端是唯一事实来源 |
| 短信**发送** | 执行 | ✅ 决策 | 云端做限额与路由决策，边缘端只执行 |
| 会话/联系人聚合 | ✗ | ✅ | 跨设备聚合只有云端能做 |
| eSIM profile 列举/切换 | ✅ 执行 | ✅ 发起与记账 | APDU 必须在本地 |
| eSIM profile **下载** | 执行 APDU | ✅ 拿激活码、对接 SM-DP+ | 需要出公网与凭据管理 |
| 卡策略（是否联网/分线） | 缓存并执行 | ✅ 权威 | 客户在网页上改，边缘端拉取 |
| 验证码提取规则 | ✗ | ✅ | 规则常改，不该逼客户重启设备 |
| 转发到钉钉/飞书/Webhook | ✗ | ✅ | 需要出公网、要重试、要审计 |
| 单机应急面板 | ✅ | ✗ | 断网时的保底能力 |
| 多租户、计费、审计 | ✗ | ✅ | — |
| 固件/模组能力矩阵 | ✅ 内置一份 | ✅ 权威并可下发 | 边缘端要能离线判断，云端要能热更新 |

### 三条分层原则

1. **贴硬件的留边缘，贴业务的留云端。** 判据是「断网时还需不需要它工作」。
2. **边缘端不做跨设备决策。** 它只认识自己这几根棒子。任何需要「看到别人」的
   逻辑（聚合、配额、路由到另一台设备）都在云端。
3. **云端不假设边缘端在线。** 所有下行都是「投递意图」，不是「同步调用」。

## 4. 从现有 VoDoge 继承的硬件真相

**这一节不是背景，是设计输入。** 下面每一条都是今天真机踩出来的，
新边缘端必须在设计上消化掉，而不是重新踩一遍。

### 4.1 模组 × 运营商的能力矩阵是真实存在的

实测：**EC20 配中国电信卡，短信收发都不通；同一根棒子换移动卡，立刻就通。**

| | 电信卡 | 移动卡 |
|---|---|---|
| `AT+CEREG?`（LTE） | `0,1` 已注册 | `0,1` 已注册 |
| `AT+CREG?`（CS） | **`0,2` 从不注册** | **`0,1` 已注册** |
| 发送 | `+CMS ERROR: 350` | `+CMGS: 97` 成功 |

原因：电信无 GSM、2G/3G 是 CDMA 而 EC20 不支持，所以 CSFB 无路；
固件的 MBN 档里只有移动的 VoLTE 档，没有电信的，所以 IMS 也起不来。
LTE 下短信只有这两条承载，两条都没有 ⇒ 网络直接拒绝。

**设计要求**：能力矩阵必须是**声明式数据**，在尝试之前就能回答
「这个组合能不能发短信」，而不是发出去等 20 秒超时。见 §5.3。

### 4.2 QMI 的 serving system 对 LTE-only 驻网是瞎的

`NAS Get Serving System` 会把已驻 LTE 的模组报成 `not-registered-searching`，
且 `MCC/MNC/RadioInterface` 全为空；同一时刻 `NAS Get Cell Location Info`
能给出 PLMN、TAC、Global Cell ID。

**设计要求**：驻网判定**永远不能只信单一信源**。见 §7.4。

### 4.3 关掉射频就必须保证能开回来

原实现在 radio cycle 中关掉射频后，若 ctx 超时就直接返回，再也走不到恢复那步；
更糟的是恢复用同一个 ctx，ctx 一旦 Done 恢复必然也失败——两个失败是**相关**的。
而「射频关闭」在系统里是个没人来救的死局：健康看门狗见到 RFOff 会主动抑制驱逐。

**设计要求**：任何「先破坏再恢复」的操作必须用**独立于业务 ctx 的收尾预算**。
见 §7.5。

### 4.4 模组不遵守协议里的过滤参数

EC20 无视 `WMS ListSMS` 的 tag 入参，把卡上的已发送存档和草稿一并返回。
代码只取 `Index` 丢掉了 `Tag`，于是拿去当来信读，失败又不消失，
每 60 秒一轮，永不收敛。

**设计要求**：**永远按返回值复核，不信入参。** 见 §7.4。

### 4.5 共享代理是共享故障域

为让 `qmicli` 能与主程序并存而启用 `qmi-proxy` 后，一个 proxy 同时持有两个
控制口；eUICC 切卡的 RESET 把它搞死，**两根模组一起失联**，且自动判定逻辑
会因为「控制口有占用」而继续选择那个已卡死的 proxy，形成死循环。

**设计要求**：共享组件必须有**健康探测与自动回退**，且故障域不得跨设备。见 §7.3。

### 4.6 切卡不能掐掉自己要用的通道

切卡前置钩子 `clear()` 整张 APDU 会话表，把 eSIM 自己正要发 EnableProfile 的
通道也清了，于是**任何设备的任何 profile 切换都必失败**。而且此前完全无法诊断——
错误只回给前端，服务端只看得到 `switch_phase: failed`。

**设计要求**：资源回收必须**按所有者/用途精确定向**；失败路径必须落日志。见 §7.6、§8.4。

### 4.7 其他零散但会咬人的事实

- **热插拔检测默认关闭**（`AT+QSIMDET: 0,0`）：带电换卡模组不会察觉，必须复位才重读卡槽。
- **`AT+CNUM` 不可信**：读的是 EF_MSISDN，运营商经常不写或写旧号，**不能当作本机号码**。
- **`lsusb` 的型号名不可信**：EC20-CE 与 EC25 共用 PID `0125`，以 `AT+QGMR` 固件串为准。
- **设备必须按 IMEI 绑定**，不能绑 `/dev/cdc-wdmN`——USB 重新枚举后节点名会变。
- **短时间反复复位模组会让恢复逻辑卡住**，需要重启进程才自愈。

## 5. 垂直工厂设计模式（核心抽象）

这是本次设计的中心。目标：**新增一个地区、一个运营商、一款模组，
只写一个工厂实现，不改任何核心流程代码。**

### 5.1 问题定义

现有代码里，差异是这样表达的：

```go
// 反面教材（现有实现的形态）
if lane == "intl" {
    if radioOK { primary = cellular; fallback = ims } else { ... }
} else {
    if vowifiActive { primary = ims } else { primary = cellular }
}
```

差异散在几十个 if 里，且**多个正交维度被压平成一个条件**：
线路（国内/国外）、模组能力（支不支持 IMS）、运营商（有没有 GSM 回落）、
卡类型（普通 USIM / eUICC）——这四个维度互相独立，却纠缠在同一串分支里。

### 5.2 三条正交轴

明确拆开：

| 轴 | 取值示例 | 决定什么 |
|---|---|---|
| **ModemFamily**（模组族） | EC20 / EC25-CN / EG25-G / UFI103S | 传输方式、支持哪些承载、AT 方言 |
| **CarrierProfile**（运营商） | CN-Mobile / CN-Unicom / CN-Telecom / HK-* / 通用国际 | 有无 GSM 回落、是否需要 IMS、短信中心、APN |
| **Vertical**（业务线路） | `cn` 国内线 / `intl` 国外线 | 出口策略、通知策略、合规策略 |

**Vertical 由人工标注，不从 MCC 推断**——这是现有产品的既定原则，继续保持。
ModemFamily 与 CarrierProfile 由运行时探测得出。

### 5.3 能力矩阵：轴的乘积

三轴的乘积决定「这台设备现在能做什么」。这是 §4.1 那个坑的正面解法。

```rust
/// 一次能力查询的结果。它回答的是「能不能」，不是「试试看」。
pub struct Capability {
    pub sms_mo: BearerSupport,      // 发短信
    pub sms_mt: BearerSupport,      // 收短信
    pub data:   BearerSupport,
    pub voice:  BearerSupport,
}

pub enum BearerSupport {
    /// 支持，并注明走哪条承载
    Supported(Bearer),
    /// 硬件/网络组合上不可能，附带人类可读的原因
    Unsupported { reason: &'static str },
    /// 需要运行时探测才知道（例如要看 IMS 有没有注册上）
    Probe,
}

pub enum Bearer { Cellular, Ims, Sgs }
```

**关键**：`Unsupported` 必须带原因，并且这个原因要能一路传到云端界面上。
今天那个「EC20 + 电信」的组合，界面上应当直接显示

> 该模组在中国电信网络下没有短信承载（无 CDMA 回落、固件无电信 VoLTE 档），
> 请改用 EC25-CN 或更换运营商

而不是让用户等 20 秒超时再看一个 `CMS ERROR: 350`。

矩阵以**声明式数据**表达，随二进制内置一份，并可由云端热更新（§9.6）：

```toml
# capability-matrix.toml（节选）
[[rule]]
modem_family = "EC20"
carrier      = "CN-Telecom"
sms_mo       = { kind = "unsupported", reason = "no_cdma_fallback_and_no_ct_volte_mbn" }
sms_mt       = { kind = "unsupported", reason = "no_cdma_fallback_and_no_ct_volte_mbn" }
data         = { kind = "supported", bearer = "cellular" }

[[rule]]
modem_family = "EC20"
carrier      = "CN-Mobile"
sms_mo       = { kind = "supported", bearer = "cellular" }
sms_mt       = { kind = "supported", bearer = "cellular" }
```

### 5.4 工厂接口

```rust
/// 垂直工厂：给定三轴，产出一族互相配套的策略对象。
///
/// 「一族」是这个模式的要点——SMS 路由、驻网策略、eSIM 策略、出口策略
/// 必须来自同一个工厂，它们之间有隐含契约（例如国外线的 SMS 回退到 IMS，
/// 前提是驻网策略允许 IMS 注册）。混搭不同工厂的产物会产生无人测试过的组合。
pub trait VerticalFactory: Send + Sync {
    fn id(&self) -> VerticalId;

    /// 这个工厂是否接管该设备。第一个返回 true 的工厂胜出。
    fn matches(&self, ctx: &DeviceContext) -> bool;

    fn sms_router(&self, cap: &Capability) -> Arc<dyn SmsRouter>;
    fn registration(&self, cap: &Capability) -> Arc<dyn RegistrationPolicy>;
    fn esim(&self) -> Arc<dyn EsimPolicy>;
    fn egress(&self) -> Arc<dyn EgressPolicy>;
    fn notification(&self) -> Arc<dyn NotificationPolicy>;
}
```

各策略是窄接口，例如：

```rust
pub trait SmsRouter: Send + Sync {
    /// 决定这条短信先走哪条承载、失败能否换一条。
    /// 纯函数，不碰硬件——便于穷举测试。
    fn plan(&self, cap: &Capability, state: &RadioState) -> SendPlan;
}

pub struct SendPlan {
    pub primary:  Option<Bearer>,
    pub fallback: Option<Bearer>,
    /// 人类可读的判据，直接进日志与界面。
    pub reason:   Cow<'static, str>,
}
```

### 5.5 注册与选择

```rust
pub struct VerticalRegistry {
    factories: Vec<Arc<dyn VerticalFactory>>,   // 按优先级有序
}

impl VerticalRegistry {
    pub fn resolve(&self, ctx: &DeviceContext) -> Arc<dyn VerticalFactory> {
        self.factories.iter()
            .find(|f| f.matches(ctx))
            .cloned()
            .unwrap_or_else(|| self.fallback())
    }
}
```

**新增一个地区 = 新增一个 `VerticalFactory` 实现 + 注册一行 + 矩阵里加几条规则。**
核心流程（驻网协调、短信收发循环、eSIM 切换）一行不改。这是本模式的验收标准。

### 5.6 为什么不用别的方案

| 方案 | 否决理由 |
|---|---|
| 配置文件里堆 `if` 表达式 | 可读性差、无类型检查、无法单测 |
| 每个运营商一个完整实现 | 代码爆炸，共性无法复用 |
| 只按 Vertical 分（不拆模组轴） | 无法表达「同一线路下不同模组能力不同」——正是 §4.1 那个坑 |
| 运行时纯探测，不要矩阵 | 每次都要试错，慢且伤硬件（见 §4.3 radio cycle） |

矩阵与探测**并存**：矩阵给出先验（`Supported`/`Unsupported`），
`Probe` 档位保留运行时探测的空间。二者互补，不是二选一。

## 7. 边缘端设计（Rust）

### 7.1 进程模型

**单进程、单二进制、零外部依赖。** 交付物是一个文件，`scp` 上去就能跑。

理由：客户机房没有运维。任何「还需要装个 Docker / 配个 systemd 依赖链」的方案
都会在售后阶段付出十倍代价。SQLite 而非 PostgreSQL 也是同一逻辑。

内部用 Tokio 多任务：

| 任务 | 职责 | 生命周期 |
|---|---|---|
| `supervisor` | 设备发现、worker 生命周期 | 常驻 |
| `worker[i]` | 一根模组的全部交互 | 随设备增删 |
| `uplink` | WS 连接、心跳、补传 | 常驻，断线重连 |
| `web` | 本地 Axum 服务 | 常驻 |
| `janitor` | 本地库滚动清理、日志轮转 | 定时 |

### 7.2 设备身份与绑定

**按 IMEI 绑定，永不绑 `/dev` 节点名**（§4.7）。

发现流程分三步，**第一步成功就不做后面的**：

1. **QMI 能力探测**——有 `qmi_wwan` 驱动 + net 接口 + `cdc-wdm` 控制节点，与 VID 无关
2. **MBIM 能力探测**——同上
3. **VID 兜底**——Quectel `0x2c7c` / Qualcomm `0x05c6` / SIMCOM，且必须有可用 AT 口

型号以 `AT+QGMR` 固件串判定，不信 `lsusb`（§4.7）。

### 7.3 传输层与故障域

每根模组**独占**自己的控制通道。**禁止跨设备共享传输组件**——§4.5 的教训。

若确需共享（例如未来引入 qmi-proxy 以支持外部工具并存），必须满足：

- 每设备一个实例，或
- 有主动健康探测 + **自动回退直连**，且回退判据不能是「控制口有占用」
  （那正是死循环的成因）

### 7.4 驻网判定：多信源仲裁

直接源于 §4.2 与 §4.4。

```rust
/// 驻网状态由多个信源仲裁得出，任何单一信源都不足以定论。
pub trait RegistrationSource {
    fn probe(&self) -> Result<RegistrationEvidence>;
    fn confidence(&self) -> Confidence;
}
```

信源优先级：**小区信息（有 PLMN + 非零 Cell ID）> AT `+CEREG` > serving system**。

仲裁规则：

- 任一高置信源报「已驻网」⇒ 判定已驻网，**不执行任何恢复动作**
- 全部信源报「未驻网」⇒ 才允许进入恢复升级路径
- 信源之间矛盾 ⇒ 记录矛盾并采信高置信源（这类矛盾要能在云端看到，
  它是发现新固件缺陷的线索）

**列表类结果一律按返回值里的 tag/type 复核，不信入参**（§4.4）。

### 7.5 破坏性操作的收尾契约

任何「先破坏再恢复」的操作（radio cycle、切卡、模组复位）必须遵守：

```rust
/// 破坏性操作的统一封装。
/// 恢复预算独立于业务 ctx —— 业务 ctx 超时恰恰是最需要恢复的时候。
pub async fn with_restore<F, R>(
    disrupt: impl FnOnce() -> Result<()>,
    restore: R,
    restore_budget: Duration,
    body: F,
) -> Result<()>;
```

**不变量**：`restore` 在**所有**退出路径上执行，且使用独立预算。见 §4.3。

### 7.6 资源回收必须定向

APDU 会话、逻辑通道等资源的回收，必须按 **所有者 + 用途** 精确定向，
禁止「清空整张表」。见 §4.6。

```rust
pub enum ReleaseScope {
    All,
    /// 除某个用途外全部释放——切卡时用它保住 eSIM 自己的通道
    AllExcept(ResourceClass),
    Owner(OwnerId),
}
```

### 7.7 离线队列语义

**这是边缘端最需要写对的部分。**

- 短信一旦解码成功，**先落 SQLite 再确认删除模组存储**。顺序不能反。
- 队列是 **at-least-once**：宁可重传，不可丢失。去重由云端按幂等键做（§9.4）。
- 每条待上传记录有单调递增的本地 `seq`，云端按 `(device_id, seq)` 去重。
- 队列有**容量上限**（默认 10 万条 / 500 MB，可配）。超限时按**最旧的非验证码类**
  优先淘汰，并产生一条告警事件——**永不静默丢弃**。
- 补传是**断点续传**：云端返回已确认的最大 `seq`，边缘端从那之后重发。

### 7.8 单机应急面板

Axum + 内嵌 SPA，前端构建产物用 `rust-embed` 打进二进制。

**能力刻意做窄**——它是保底，不是第二套控制台：

| 有 | 没有 |
|---|---|
| 看本机短信（近 N 天） | 多设备聚合、历史全量 |
| 看信号/驻网/SIM 状态 | 计费、租户、审计 |
| 手动发一条短信 | 规则、自动转发 |
| 重启模组、重连云端 | eSIM 下载（需云端凭据） |
| 看与云端的连接状态和队列积压 | — |

访问控制：**默认只监听局域网**，首次启动生成随机密码并打印到串口/日志；
可在云端下发新密码。

### 7.9 自更新

云端下发「目标版本 + 签名 + 下载地址」，边缘端自行下载、校验签名、
原子替换、重启。**必须支持回滚**：新版本启动后 N 分钟内未能与云端握手成功，
自动回退上一版本。

## 8. 云端设计

### 8.1 控制台（Next.js）

多租户靠 **Edge Middleware 解析 Host**：

```
a.vodoge.com  →  middleware 提取 subdomain "a"
              →  查租户表得 tenant_id
              →  注入请求上下文，后续所有查询自动带上

父域 vodoge.com 不是租户；未知子域必须 404，不能回落默认租户。
```

**租户解析失败必须 404，不能回落到默认租户**——这是安全边界。

实时推送用 **SSE**（不是 WS）：控制台只需要单向的服务器推送，SSE 更简单、
自动重连、能穿透大多数企业代理。指令下发走普通 HTTP POST。

### 8.2 网关（Go）

职责**刻意做薄**——它只做四件事：

1. 维持海量 WSS 长连接，管心跳与超时
2. 认证设备身份，把连接绑定到 `(tenant_id, device_id)`
3. 上行：校验信封 → 写 PostgreSQL → 发 Redis 事件通知控制台
4. 下行：订阅 Redis 指令频道 → 找到对应连接 → 投递 → 回传 ack

**不做**：业务规则、验证码提取、转发。那些在控制台侧的后台任务里做。
理由：网关要能随连接数水平扩容，业务逻辑放进去会让扩容变成难题。

连接路由：网关多实例时，每个实例把自己持有的 `device_id` 注册进 Redis
（`device:{id}:node → node_id`，带 TTL 心跳续期）。下发指令时按此定位实例。

### 8.3 Redis 的角色

**只做分拣，不做存储。** 所有需要持久的东西都在 PostgreSQL。

| 用途 | 键/频道 | 说明 |
|---|---|---|
| 指令下发 | `cmd:{node_id}` | 控制台发布，网关订阅 |
| 设备在线注册 | `device:{id}:node` | 带 TTL，心跳续期 |
| 新事件通知 | `evt:{tenant_id}` | 网关发布，控制台 SSE 订阅 |

Redis 挂掉时：**已建立的长连接不受影响，上行照常入库**；只有下发指令暂时不可用。
这个降级特性要在设计上保证，不能让 Redis 成为上行的必经之路。

### 8.4 可观测性（硬性要求）

§4.6 的教训：**失败必须落日志，且带足够上下文。**

强制规则，写进 CI 检查：

- 任何返回 `error` 的路径，要么记日志，要么把错误**原样**返回给会记日志的调用方
- **禁止**吞掉 error（`_ = doSomething()` 需要显式注释说明为什么可以吞）
- 每条错误日志必须带：`tenant_id`、`device_id`、操作名、可关联的 `trace_id`
- 面向用户的错误信息与日志里的技术原因**分开**：用户看「该模组在电信网络下
  没有短信承载」，日志里同时有 `CMS ERROR: 350` 和能力矩阵的判定依据

## 9. 边缘 ↔ 云 协议规格

**这是两个仓库的接缝，必须先定死。** 两边可以并行开发的前提是这一节不再变。

### 9.1 传输

- **WSS over 443**，边缘端主动发起。选 443 是为了穿透企业防火墙。
- **TLS 1.3 only**（按 RFC 9846）：客户端与网关都把最小和最大协议版本固定为
  TLS 1.3；TLS 1.2 及以下一律拒绝，禁止为旧设备做降级重连。
- WSS 长连接必须使用 **mTLS**：网关验证边缘端设备证书，边缘端验证网关证书链；
  任何一侧不得关闭证书校验或接受匿名客户端。
- 不发送 TLS 0-RTT 应用数据。上行补传与下行指令都可能改变状态，重放风险不能靠
  TLS 层的早期数据去赌；恢复会话后仍先完成握手，再发送协议信封。
- TLS 1.3 的 AEAD 密码套件由运行时的 TLS 1.3 实现协商，不手工启用旧套件；
  部署 CI 必须断言实际协商版本为 TLS 1.3。
- 二进制帧，**MessagePack** 编码（比 JSON 省带宽，比 Protobuf 少一层代码生成）。
- 心跳：边缘端每 30s 发 `ping`，云端 90s 未收到则判定离线。

### 9.2 认证

设备首次注册时，客户在控制台生成**一次性注册码**；边缘端用它换取长期
**设备证书**（mTLS 客户端证书）与 `device_id`。此后每次连接用证书认证。

理由：一次性码可以放心贴在部署文档里；证书泄露可单设备吊销，不影响其他设备。

注册码兑换接口本身也只接受 TLS 1.3。设备私钥在边缘端本地生成并保存，注册服务
只签发 CSR，绝不把私钥经网络传回；证书必须带 `device_id`、`tenant_id` 与 `region`
受限标识，网关以证书主体而不是信封字段判定身份与区域。证书轮换采用重叠有效期：
边缘端用仍有效的旧证书申请新证书，旧证书过期或被吊销后立即拒绝。

### 9.3 消息信封

```
Envelope {
  v:         u8          // 协议版本，当前 1
  kind:      MessageKind // 见下
  id:        Uuid        // 本条消息唯一 ID
  ts:        i64         // 边缘端本地毫秒时间戳
  device_id: String
  seq:       Option<u64> // 仅上行业务消息有；单调递增，用于补传定位
  payload:   bytes
}
```

`tenant_id` **不在信封里**——由网关从连接的证书推导。
让边缘端自报租户等于把越权的钥匙交出去。

### 9.4 上行消息

| kind | 载荷 | 幂等键 | 说明 |
|---|---|---|---|
| `SmsReceived` | 发件人、内容、时间、ICCID、承载 | `(device_id, seq)` | 核心业务 |
| `DeviceState` | 信号、驻网、SIM、能力判定结果 | 覆盖式 | 定期 + 变化时 |
| `CommandResult` | `cmd_id`、成功/失败、原因 | `cmd_id` | 对应下行指令 |
| `EsimInventory` | EID、profile 列表 | 覆盖式 | 切卡后刷新 |
| `Alert` | 级别、代码、上下文 | `(device_id, seq)` | 队列超限、能力不支持等 |

**至少一次投递**。云端按幂等键去重，边缘端收到 ack 后才从队列删除。

### 9.5 下行指令

| kind | 载荷 | 说明 |
|---|---|---|
| `SendSms` | 目标号码、内容、指定设备/ICCID | 云端已做完限额与路由决策 |
| `RestartModem` | 设备/模组标识 | |
| `SwitchEsimProfile` | 目标 ICCID | 边缘端执行 APDU |
| `UpdateCardPolicy` | 是否联网、分线、APN | 边缘端缓存并执行 |
| `UpdateCapabilityMatrix` | 矩阵内容 + 版本 | 见 §9.6 |
| `SelfUpdate` | 版本、URL、签名 | 见 §7.9 |

每条指令有 `cmd_id`；边缘端**必须**回 `CommandResult`，成功失败都要回。
云端对未回执的指令做超时标记，不无限等待。

### 9.6 能力矩阵热更新

矩阵带版本号。边缘端连接建立时上报本地版本，云端版本更高则下发新矩阵。

意义：发现一个新的「模组 × 运营商」不支持组合时，**不需要给几万台设备发新固件**，
改云端数据即可。这是 §5.3 把矩阵做成数据而非代码的直接收益。

### 9.7 契约的单一来源

协议定义写在**一份 schema 文件**里，同时生成：

- Rust 结构体（`vodoge-edge/contract`）
- Go 结构体（`vodoge-cloud/packages/contract`）
- TypeScript 类型（同上）

**禁止手写三份。** CI 检查生成物与 schema 一致，不一致即失败。
理由：现有项目已经吃过「路由表、SSE 白名单、OpenAPI spec 三处分叉」的亏，
那次是漏改白名单导致 SSE 全部 401 而编译测试全绿。

## 10. 数据模型与租户隔离

### 10.1 隔离策略：字段隔离 + RLS

**模型：一套 PostgreSQL，共享表，每张业务表带 `tenant_id` 判别列，用 RLS 强制。**

不做 database-per-tenant、schema-per-tenant，也**不按区域拆业务库**。理由：

- 现阶段就一套库、一套迁移，运维和 CI 都简单；租户之间靠字段 + RLS，不靠分库
- 客户是企业，数量在几百到几千量级——每租户/每区域一套库会让每次迁移要跑 N 遍
- 真出现单租户数据量问题，**先做分区表**（§10.3）比换隔离模型代价小得多
- 区域（`cn` / `intl`）是租户上的字段，也写进设备证书，供网关拒接错区的连接；
  它不是第二套数据库。以后若合规强制物理隔离，再把某区域迁走，而不是一开始就分库

**RLS 的强度不在于「字段」，而在于规则写死在数据库内核里**——应用代码写错也越不过去。
但它有三个必须堵死的失败路径，堵不住则整套防线作废。

#### 三层防护

1. **应用层**：所有查询经统一的 repository，强制带 `tenant_id`
2. **数据库层**：每张业务表 `ENABLE` **且** `FORCE` RLS
3. **连接层**：应用用**非超级用户**角色连库

#### 失败路径一：owner 默认绕过 RLS

只写 `ENABLE ROW LEVEL SECURITY` **不够**——表的所有者仍然绕过策略。
必须两条都写：

```sql
ALTER TABLE messages ENABLE ROW LEVEL SECURITY;
ALTER TABLE messages FORCE  ROW LEVEL SECURITY;  -- owner 也不放过
```

超级用户则是**任何情况下都绕过 RLS**，所以第 3 层不是可选项。

#### 失败路径二：连接池 + 会话变量（最危险）

`current_setting('app.tenant_id')` 是**会话级**的，而 pgBouncer 在 transaction
模式下会把同一条连接在事务之间复用给不同请求。用 `SET` 设置的值会**残留**到
下一个请求——直接跨租户泄漏，且静默无声。

**强制写法**，三个要素缺一不可：

```sql
BEGIN;
SET LOCAL app.tenant_id = '...';   -- LOCAL：事务结束即失效，不残留
SELECT ...;
COMMIT;
```

repository 层必须把「开事务 + `SET LOCAL`」封装成唯一入口，
**禁止任何代码路径绕过它直接拿连接执行查询**。

#### 失败路径三：新表忘了开 RLS

加一张表、漏写 policy，就是一个静默的洞：不报错、测试照常绿。
这与本项目历史上「路由表三处分叉，漏改一处导致 SSE 全部 401 而 CI 全绿」
是同一类问题——**靠人记住是不可靠的，必须让漏不掉**。

对策：CI 遍历业务 schema 下每张表，任一张没有 `FORCE` RLS 或缺少策略即失败。
见任务 `C-02b`。

### 10.2 核心表

```sql
tenants(id, slug, name, status, region, created_at)  -- id 即 tenant_id；region 是字段
users(id, tenant_id, email, role, ...)
devices(id, tenant_id, imei, name, vertical, last_seen_at, state jsonb)
modems(id, device_id, tenant_id, family, firmware, iccid, imsi, capability jsonb)
messages(id, tenant_id, device_id, modem_id, direction, peer, body,
         bearer, received_at, seq, dedupe_key)
commands(id, tenant_id, device_id, kind, payload jsonb,
         status, issued_at, acked_at, result jsonb)
rules(id, tenant_id, name, matcher jsonb, action jsonb, enabled)
audit_log(id, tenant_id, actor, action, target, detail jsonb, at)
```

**`jsonb` 的用法边界**：用于**形状会变**的东西（模组指标、硬件日志、规则定义）。
凡是要索引、要外键、要约束的字段，一律用正经列。
反面教材是「把整个设备状态塞进一个 jsonb 然后到处 `->>`」。

### 10.3 索引与保留

- `messages` 按 `(tenant_id, received_at desc)` 与 `(tenant_id, peer)` 建索引
- `messages(device_id, seq)` 唯一索引 —— 幂等去重靠它
- 保留期按租户配置，超期归档到冷存储

**幂等是数据正确性的底线，不是计费的附属功能**（§14.3）。即使 MVP 不计费，
`(device_id, seq)` 唯一约束也必须从第一天就有——补传场景下它是防重复的唯一屏障，
将来要按条数统计时也只有它能保证历史数据可回溯。

#### 什么时候上分区表

`messages` 是唯一会长到需要分区的表。**不要一开始就分**——分区会让唯一约束、
外键和查询计划都复杂化，在数据量不够时是纯负担。

**触发判据**（满足任一即启动分区改造）：

- `messages` 行数 > 5,000 万，或
- `(tenant_id, received_at desc)` 索引大小超过内存可缓存范围，查询 P95 明显劣化，或
- 出现单个租户数据量占比 > 30% 的「大象租户」，拖累其他租户

**分区方式**：按 `received_at` 做 **range 分区**（月/周），不按 `tenant_id` 做 hash 分区。

理由：时间分区能直接服务于**保留期归档**（老分区整个 detach 掉即可），
而租户分区解决不了归档问题，且租户增删会导致分区数量不断漂移。
「大象租户」用更细的时间分区粒度或归档解决，**不改隔离模型、不因此分库**。

### 10.4 区域是字段，不是分库（§14.2 决定）

**模型：与 §10.1 同一套库。** `tenants.region ∈ {cn, intl, ...}` 只描述租户归属；
设备证书的 OU 也带 region，网关用来拒接配错区的设备。业务行不因 region 换库。

```
PostgreSQL（一套）
  tenants(id, slug, name, status, region, ...)
  devices / modems / messages / commands / rules / audit_log
  ─ 每张业务表有 tenant_id，RLS 按 tenant_id 隔离
```

**四条规则**：

1. **租户的 `region` 在创建时确定，此后不可变更。** 要换区域＝新建租户 + 数据迁移，
   走人工流程。允许在线改会让证书、网关配置和目录字段互相打架。
2. **业务查询按 `tenant_id` 隔离，不按库隔离。** 控制台解析 Host 得到 slug 后，
   用同库的租户目录换成 `tenant_id`，后续查询 `SET LOCAL app.tenant_id`。
3. **网关可以按区域部署，但不是必须分库。** 边缘设备连到自己租户所属区域的网关；
   证书里的 region 与网关配置不一致则拒绝。同一套库可以给多个网关实例用。
4. **没有单独的「只存路由、不存业务」的全局库。** 租户目录和短信、指令在同一个
   PostgreSQL 里。slug → tenant 的解析结果仍然**必须缓存**，避免每个 HTTP 请求
   都打一次目录表。

**对 §8.1 的影响**：Edge Middleware 解析 Host 得到 slug 后，查同库 `tenants`
拿 `tenant_id`（以及 region、status）。未知 slug **404**，不回落默认租户。

**对 §9.2 的影响**：设备注册时签发的证书里写入 region，
网关校验「证书 region == 本网关 region」，不匹配即拒绝连接。

## 14. 决策记录

2026-08-20 全部拍板。以下是决定、理由，以及**遗留风险**。

### 14.1 硬件层：全 Rust，自己实现 QMI/MBIM 协议

**决定**：不做技术验证，直接按全 Rust 开工，QMI/MBIM 编解码自己写。

调研结论（决策依据）：

| Rust 侧 | 实际情况 |
|---|---|
| `libqmi-glib-rs` v0.1.4 | **243 次下载**，且是 C 版 libqmi 的 FFI 绑定，非纯 Rust |
| `libqmi-glib-sys` v0.1.0 | 195 次下载，裸 FFI |
| `qmi-sim-manager` v0.1.2 | 109 次下载，v0.1 早期 |
| **MBIM** | crates.io 与 GitHub **均无实现** |

也就是说：**没有可用的现成轮子，FFI 路线还会把单二进制交付这条卖点破坏掉**
（要动态链接 libqmi，等于把 CGO 的问题原样搬来）。既然两条外部路线都不理想，
自己实现反而是唯一能同时满足「纯 Rust + 单文件交付」的路径。

> **遗留风险（明确记录，不粉饰）**：这是本项目最大的单点风险。
> 参照物是现有 Go 实现——`pkg/mbim` 4.2k 行、`internal/qmi` 2.7k 行，
> 且依赖外部的 `quectel-qmi-go`。新实现要在 Rust 里把这些重新走一遍，
> 工期不可控，且 §4 里那四个 bug 要在新实现中重新验证。
>
> **缓解措施**：§12 把协议层提到最前面（`E-P1`~`E-P5`），
> 并设**中止判据**——见 §12「阶段 P」。宁可早失败早换路线，
> 不要在业务层堆了三个月之后才发现协议层填不平。

### 14.2 多区域：字段，不是分库

**决定（修订）**：多租户隔离用共享表 + `tenant_id` + RLS（§10.1）。
区域是 `tenants.region` 字段和证书 OU，**不按区域拆 PostgreSQL**。

原先曾考虑「控制面单库 + 每区域一套数据面」。现阶段租户量和运维人手都撑不起
两套库两套迁移；真要合规物理隔离，再把某区域的数据迁走，而不是一开始就分。

对设计的影响见 §10.1、§10.4。

### 14.3 计费：MVP 不做

**决定**：不实现计费与配额，但 `messages` 表保留足够信息以便日后回溯统计。

**约束**：即使不计费，也**必须**保证 §7.7 的幂等语义——否则将来按条数计费时，
补传场景会重复计数，历史数据无法回溯修正。**幂等不是计费的功能，是数据正确性的底线。**

### 14.4 老版本归宿与控制台语言

**决定**：

- 现有单机 VoDoge（本仓库）**冻结**：不再加功能，只修严重 bug，
  作为新架构的参考实现与应急备用。
- 新控制台**延续中英双语**。现有产品已有 i18n 基建，成本低；
  且多区域方案下必然会有海外客户。
